\section{System Overview}

We place a runtime enforcement layer around a multi-agent system, independently of
its agent framework or application backend. The design combines a common action gate
with application-selected information-flow control (IFC), capability control, and
resource finite-state-machine (FSM) mechanisms. Policies and security state are
represented as Datalog facts and rules; trusted adapters connect them to observations
and actual effects. The prototype implements the generic local action gate and Nova's
message profile. Resource FSM inference is implemented; protected FSM execution is a
specified integration step rather than an implemented prototype guarantee.

\begin{mainbox}
\centering
\textbf{Distributed facts + Datalog policies}\\[5pt]
\small
\begin{tabular}{ccccc}
\textbf{Query} & \textbf{Why} & \textbf{What-if} & \textbf{Min-prevention} & \textbf{Planning}\\
matching facts & proof & changed inputs & fewest prevented events & path to a goal
\end{tabular}
\end{mainbox}

The same representation supports five analysis modes:
\begin{itemize}
\item \textbf{Query.} Find facts matching a user-supplied query.
\item \textbf{Why.} Explain why a selected fact holds, tracing a proof back to inputs.
\item \textbf{What-if.} Add or remove input facts and ask whether a selected fact still holds.
\item \textbf{Min-prevention.} Find the smallest sets of preventable events whose removal makes a selected fact no longer hold.
\item \textbf{Planning.} Find a path to a goal using the allowed actions.
\end{itemize}

Facts do not need to be stored globally. Nova keeps principal-local facts and explicit
message transfers. Other applications may use a single authoritative resource service.
Rules can be replicated; state placement, transfer routes and evaluation phases belong
to a validated execution profile rather than being inferred from tuple names.

\section{Application Porting Boundary}\label{sec:porting}

An application does not have to run on Grokbot. It supplies a trusted adapter around
the operations whose effects must be controlled. Grokbot is one adapter; the shared
runtime has no dependency on its UI, service, model provider or principal names.
An in-process TypeScript action SDK is implemented. A non-TypeScript application can
target the same boundary through a future authenticated service/gateway adapter;
that transport and its transaction guarantees are not implemented by merely exposing
a policy-check endpoint.

\subsection{Four application inputs}

\begin{enumerate}[leftmargin=1.5em,itemsep=3pt]
\item \textbf{Policy.} Natural-language requirements or reviewed Datalog, application
relations, constraints and goals. Translation targets the actual enabled contract.
Direct rules must pass the same installation checks as generated rules.
\item \textbf{Mechanism configuration.} The selected IFC/capability/FSM foundations
and application parameters: grants, groups, resource types, states and transitions.
The runtime supplies mechanisms; applications supply their domain definitions.
\item \textbf{Execution protocol.} Logical stores, fact and rule placement, allowed
exports/imports, closure phases, decision hooks and effect/commit/recovery behavior.
Authors can request a plan; it must be supported by actual adapter hooks and authority.
\item \textbf{Observation binding.} Implemented producers for EDB: authenticated
identity/configuration, authoritative snapshots, successful runtime events and verified
protocol imports. Each binding specifies argument mapping, scope, writer authority,
validity/version and completeness where absence is meaningful.
\end{enumerate}

The application author provides policy and business FSM definitions. The integration
developer supplies trusted observation/effect hooks and selects a supported execution
profile. One person may perform both roles. Neither policy text nor generated code can
invent an authenticated source, grant authority, or release a protected payload.
Current descriptions remain \texttt{app.md}, \texttt{policy.md}, \texttt{tools.md} and
\texttt{agents/*.md}; episodes are optional. The version-1 \texttt{runtime.json} binds
local input/derived schemas, gate roles and acceptance cases. The richer protocol and
source contract described here is a target, not a manifest format already supported
by the prototype.

\subsection{Mechanisms and mediated effects}

The kernel supplies validated bounded inference, the selected gate semantics, scoped
state and ordering around an actual protected operation. Optional builtin modules
supply reusable IFC, capability and FSM semantics. A builtin includes both rules and
the mechanisms that produce trusted inputs and act on designated decisions. A schema
named \texttt{Received} or \texttt{ResourceState} alone cannot establish successful
delivery or a committed transition. Roles, grants, exposure thresholds, auditor goals,
state names and business transitions remain application definitions.

The generic gate permits a request only with explicit \texttt{Allow} and no
\texttt{Deny}; Nova's receive profile permits a well-formed attempt after complete
evaluation when no \texttt{DenyReceive} is derived. The profile declares this choice.
A preview decision is not a reusable execution token. An adapter must keep identity,
operation, resource, snapshot and attempt identity bound through the actual effect.
Remote adapters need appropriate transactions, idempotency and reconciliation; a
timeout does not prove that an external effect did not occur.

Complete mediation is a deployment assumption. Incoming content must be checked
before entering an inbox or model context. Reads and tool results must be observed
if their information is to be tracked in later outputs. In-process wrappers do not
isolate malicious host code or protect access paths that bypass those wrappers.

\subsection{Stores, closure and EDB sources}

For a local decision at location $\ell$, the runtime uses a validated committed
snapshot $E_\ell^v$, stages the attempt input $I$, and evaluates the assigned rules
$R_\ell$ to their stratified fixed point:
\[
C_\ell^{v,I}=\operatorname{Closure}(E_\ell^v\cup I,R_\ell).
\]
The gate checks this result before the effect under its serialization/transaction
contract. On confirmed commit, state and successful observations change; derived
views are invalidated or recomputed for the new version. Query, Why and What-if use
the same installed program and a selected snapshot. Observers evaluate only declared
observer rules over authorized evidence and cannot silently supply a global join to
local enforcement.

Each EDB must have an implemented producer. For example, an approval-service snapshot
produces \texttt{Approval(D,A)}, while a successful receive hook produces
\texttt{Received(P,M)}. An agent's claimed approval belongs in a distinct
unverified relation. Source names resolve to trusted mapping functions, not arbitrary
model-authored code. Configuration/snapshot updates must handle removals and revocation;
committed event history has its separately declared historical meaning.

Negation requires a complete authoritative scope at the decision version. Missing,
stale or foreign-local evidence is not a proven negative. Installation must check body
locality through helpers/recursion and require an authorized evidence route for a remote
dependency. The present prototype checks schemas and selected placements but does not
yet completely validate this contract; finite installation cases do not establish it.

\section{Running Example: Nova Budget Audit}

\subsection{Application}

\textbf{Setting.} Consider a company whose departments are represented by agents. These
agents use AI tools to organize documents and review finances, and their coordination
naturally transfers information across departmental boundaries. Access is constrained by
capabilities---for example, reviewing personnel data requires an HR review
capability---and by organization-wide policies that limit how information may accumulate
across transfers.

\textbf{Scenario.} The company is launching project Nova. Its executive board assigns
Procurement, Facility, and HR to prepare their respective budget rationales, with HR
responsible for hiring costs. Two peer auditors must jointly check all three parts.
Under the company's \emph{Three-Part Exposure Policy}, no agent other than the board may
acquire all three distinct parts of a project's rationale. Auditor A holds the
\texttt{hr\_review} capability required for the hiring part; Auditor B does not. The
auditors must therefore find a division of work that completes the audit without
violating either the capability requirement or the exposure policy. The audit is
complete once each part has been received by an authorized auditor for review.

\subsection{Tuples}

Input tuples record configuration, source labels, communication inputs, and runtime
 events; derived tuples capture information flow, policy decisions, and audit progress.
In the schemas below, \texttt{P} is a principal, \texttt{A} an auditor, \texttt{M} a
message, \texttt{Tag} a knowledge label, \texttt{Group} a protected group, and
\texttt{Cap} a capability. \texttt{Min} and \texttt{Mout} denote input and output messages.
All arguments are represented as Souffl\'e symbols. The current implementation uses
single tags such as \texttt{nova\_hiring}; \texttt{TagGroup} associates tags with Nova.

Every input record belongs to a principal's local store. Shared configuration is
explicitly replicated into those stores. Records also carry source, lifetime, and
optional event metadata; these are runtime metadata rather than Datalog arguments.
Derived tuples are recomputed from local inputs. The prototype hosts all stores in
one service and persists them in one checkpoint; locality is enforced at evaluation,
not by separate machines or databases. The observer's union of stores is for inspection,
not a global join used to decide delivery.

\textbf{Trusted source labels and propagation.} The trusted application supplies
\texttt{TrustedSource(m0, nova\_hiring)} at Board. Agents cannot assign trusted source
labels. For ordinary sends, the runtime records dependencies on all earlier successful
receives by the sender. Datalog propagates tags along those dependencies. Source
assignments are trusted ingestion, not computations over Board's entire history.

\textbf{Communication boundary: \texttt{TransportTag} versus \texttt{Received}.}
The sender derives \texttt{MessageTag(M, Tag)}. The runtime exports these labels with
the message and imports them into the receiver's store as \texttt{TransportTag(M, Tag)}.
This input says what the message carries, not that delivery has succeeded. Rule R2
turns it into a local derived \texttt{MessageTag} tuple. The separate name distinguishes
protocol inputs from derived facts; it introduces no additional knowledge category.

Before checking delivery, the receiver has \texttt{Incoming(P, M)} and temporary
\texttt{TransportTag} records, but no \texttt{Received(P, M)} for this message. If local
inference derives \texttt{DenyReceive(P, M)}, the runtime discards the incoming intent
and its imported tags without recording a receive. Otherwise it retains the tags,
removes \texttt{Incoming}, and records \texttt{Received}.
Only then can the message contribute to \texttt{HasReceivedTag}. Missing inputs or an engine
failure abort evaluation rather than permit delivery. There is no explicit
\texttt{AllowReceive} predicate.

\textbf{Global audit completion.} An auditor derives \texttt{Covered(Tag)} from
successful receipt and its configured auditor role. No audit summary is sent to Board.
The global observer combines independently computed local closures and evaluates
only \texttt{Finished} rules. It never reruns local enforcement rules on that union,
and local rules cannot depend on \texttt{Finished}. The demo keeps its designated
auditors fixed. Completion means receipt for review, not a subsequent
budget judgment or a permanent audit certificate.

\subsection{Datalog Rules}

The following are the 11 information-flow, communication, and audit rules, in Souffl\'e syntax (\texttt{!} denotes
negation; quoted values are constants). Local rules use one owner's inputs.
For \texttt{HasReceivedTag} and \texttt{DenyReceive}, the principal variable in the rule head
is bound to that owner. The \texttt{Finished} rule runs only in the global observer. Board is exempt
from the three-tag constraint, but not from capability requirements.

\begin{lstlisting}
% R1: trusted-label
MessageTag(M, Tag) :- TrustedSource(M, Tag).

% R2: message-label
MessageTag(M, Tag) :- TransportTag(M, Tag).

% R3 was removed: audit progress is no longer transported.

% R4: runtime-dependency
MayDependOn(Mout, Min) :-
    Received(P, Min), Sender(P, Mout), ReceivedBeforeSend(Min, Mout).

% R5: label-propagation
MessageTag(Mout, Tag) :- MayDependOn(Mout, Min), MessageTag(Min, Tag).

% R6: received-tag
HasReceivedTag(P, Tag) :- Received(P, M), MessageTag(M, Tag).

% R7: capability
DenyReceive(P, M) :-
    Incoming(P, M), MessageTag(M, Tag), Requires(Tag, Cap),
    !HasCap(P, Cap).

% R8: three-tag-exposure (two known tags, one incoming)
DenyReceive(P, M) :-
    Incoming(P, M), MessageTag(M, T3),
    HasReceivedTag(P, T1), HasReceivedTag(P, T2),
    TagGroup(T1, Group), TagGroup(T2, Group), TagGroup(T3, Group),
    P != "board", T1 != T2, T1 != T3, T2 != T3.

% R9: three-tag-two-incoming (one known tag, two incoming)
DenyReceive(P, M) :-
    Incoming(P, M), MessageTag(M, T2), MessageTag(M, T3),
    HasReceivedTag(P, T1),
    TagGroup(T1, Group), TagGroup(T2, Group), TagGroup(T3, Group),
    P != "board", T1 != T2, T1 != T3, T2 != T3.

% R10: three-tag-all-incoming
DenyReceive(P, M) :-
    Incoming(P, M),
    MessageTag(M, T1), MessageTag(M, T2), MessageTag(M, T3),
    TagGroup(T1, Group), TagGroup(T2, Group), TagGroup(T3, Group),
    P != "board", T1 != T2, T1 != T3, T2 != T3.

% R11: coverage
Covered(Tag) :- Auditor(A), Received(A, M), MessageTag(M, Tag).

% R12: finished
Finished(Group) :-
    AuditGoal(Group, T1, T2, T3),
    Covered(T1), Covered(T2), Covered(T3).
\end{lstlisting}

\subsection{Example State}

\textbf{Configuration.} The company has two auditors, A and B. Of the two, only A
holds \texttt{hr\_review} and may receive HR information. HR also holds this capability
to receive its own tagged task from the board.

\begin{lstlisting}
% config
Auditor(auditor_a).  Auditor(auditor_b).
HasCap(auditor_a, hr_review).
HasCap(hr, hr_review).
Requires(nova_hiring, hr_review).
TagGroup(nova_procurement, nova).
TagGroup(nova_facility, nova).
TagGroup(nova_hiring, nova).
AuditGoal(nova, nova_procurement, nova_facility, nova_hiring).
\end{lstlisting}

\textbf{Messages so far.} The board has sent each department its task with the
corresponding tag: \texttt{mP0} to Procurement, \texttt{mF0} to Facility, and
\texttt{m0} to HR. Procurement and Facility have already sent their budget rationales
\texttt{mP} and \texttt{mF} to Auditor A for review. HR is now sending its hiring
rationale \texttt{mH} to A; delivery is pending a policy check. The relevant input
facts are shown by owner below. Shared configuration is replicated; each capability
fact resides only with its holder. Constants are shown unquoted in these illustrative
snapshots and query templates:

\begin{lstlisting}
% Board store: assignments and trusted source labels
TrustedSource(mP0, nova_procurement).
TrustedSource(mF0, nova_facility).
TrustedSource(m0, nova_hiring).
Sender(board, mP0).  Sender(board, mF0).  Sender(board, m0).

% Procurement store
TransportTag(mP0, nova_procurement).
Received(procurement, mP0).
Sender(procurement, mP).  ReceivedBeforeSend(mP0, mP).

% Facility store
TransportTag(mF0, nova_facility).
Received(facility, mF0).
Sender(facility, mF).  ReceivedBeforeSend(mF0, mF).

% HR store
TransportTag(m0, nova_hiring).
Received(hr, m0).
Sender(hr, mH).  ReceivedBeforeSend(m0, mH).

% Auditor A store: Procurement and Facility received; Hiring pending
TransportTag(mP, nova_procurement).
TransportTag(mF, nova_facility).
TransportTag(mH, nova_hiring).  % temporary until delivery is allowed
Received(auditor_a, mP).
Received(auditor_a, mF).
Incoming(auditor_a, mH).

% No audit-summary input at Board.
\end{lstlisting}

\textbf{Derived result.} The IFC rules propagate the board's tags to the department
replies. A already knows the Procurement and Facility parts, so receiving the Hiring
part would violate the Three-Part Exposure Policy. The rules therefore derive
\texttt{DenyReceive(auditor\_a, mH)}, even though A holds \texttt{hr\_review}.
The union of independently evaluated local closures includes:

\begin{lstlisting}
MayDependOn(mP, mP0).  MessageTag(mP, nova_procurement).
MayDependOn(mF, mF0).  MessageTag(mF, nova_facility).
MayDependOn(mH, m0).   MessageTag(mH, nova_hiring).
HasReceivedTag(auditor_a, nova_procurement).
HasReceivedTag(auditor_a, nova_facility).
Covered(nova_procurement).
Covered(nova_facility).
DenyReceive(auditor_a, mH).
\end{lstlisting}

The runtime blocks \texttt{mH}, so neither \texttt{Covered(nova\_hiring)} nor
\texttt{Finished(nova)} is derived.


\section{Resource Lifecycle Foundation}

Resource lifecycle is a reusable builtin mechanism selected by an application. The
application supplies resource types, states, transitions and policy guards; the runtime
is responsible for safe transition execution and committed state/history. Nova's
message lifecycle remains separate from such a business resource workflow, and neither
requires enumerating every combination of accumulated IFC tags as an FSM state.
A shared machine is defined by resource type; each resource retains its own current
state and action history:
\begin{lstlisting}
ResourceType(Resource, Type).
ResourceState(Resource, State).
Transition(Type, Action, From, To).
ActionTaken(Event, Resource, Action, From, To).
\end{lstlisting}
These are input predicate schemas with different writers: the trusted registry supplies
types/initial state, the app authority supplies transitions, and the protected executor
maintains current state and success history. An agent cannot assert a successful action.
The same machine serves every matching resource. The implemented inference validator
rejects conflicting current states or types and ambiguous transitions for the same
type, action, and source state. The following predicates are derived:

\begin{lstlisting}
EnabledAction(R, From, Action) :-
    ResourceType(R, Type), Transition(Type, Action, From, To).
ReachableState(R, From, To) :-
    ResourceType(R, Type), Transition(Type, Action, From, To).
ReachableState(R, From, To) :-
    ReachableState(R, From, Mid),
    ResourceType(R, Type), Transition(Type, Action, Mid, To).
\end{lstlisting}

\texttt{EnabledAction(R, State, Action)} describes actions enabled by the FSM in a
specified state, whether or not that state is current. Likewise,
\texttt{ReachableState(R, From, To)} describes reachability from a specified state,
independently of the current state. Reachability requires at least one transition;
a state reaches itself only through a nonempty cycle. To ask about the current state,
join with the input predicate explicitly:
\begin{lstlisting}
?- ResourceState(R, State), EnabledAction(R, State, Action).
?- ResourceState(R, From), ReachableState(R, From, Target).
\end{lstlisting}

These rules describe the supplied FSM structure. They neither produce an executable
action path nor authorize an operation. In the target execution contract, a request
must satisfy both the current-state transition and the application gate:
\[
\begin{split}
\operatorname{execute}(q,r,a)\ \Longrightarrow\;&
 \operatorname{ResourceState}(r,s)\ \land\
 \operatorname{Transition}(\operatorname{type}(r),a,s,s')\\
 &\land\ \operatorname{Allow}(q)\in C_\ell^{v,I}
 \ \land\ \nexists d:\operatorname{Deny}(q,d)\in C_\ell^{v,I}.
\end{split}
\]
The snapshot must be admissible and the transition uniquely determined. Under a
per-resource serialization/transaction boundary, the executor reads current state,
evaluates guards/authorization, invokes the real operation, then replaces the current
state and records \texttt{ActionTaken} only after confirmed success. Denial or a
confirmed no-effect failure creates no successful transition. An uncertain external
outcome requires recovery before an incompatible retry; a callback cannot undo a
completed external write. Multi-worker exclusivity requires a shared state authority.

\textbf{Implementation boundary.} The lifecycle module currently implements only
validation and structural inference. The generic action SDK serializes authorization,
callback and additive observations within one process-local session. It does not yet
integrate FSM state replacement or recovery. Protected FSM execution is therefore a
required builtin integration step in this design, not a demonstrated current feature.
No business-resource workflow is connected to Nova.

Changing current state changes the results of the joins above, not the machine's
state-indexed enabled actions or reachability. Historical action records remain.
Explaining a past action requires its pre-action facts and the rule version used then,
rather than today's resource state.

\section{High-Level Analysis Questions}\label{sec:analysis-questions}

Let \(E=(E_P)_P\) be the collection of local input stores. For a local query,
\(\mathrm{Closure}(E)\) denotes the selected owner's closure; a Board completion query
uses Board's closure. Analysis never runs the policy on a union of all input stores.
The five UI tabs describe analysis methods, independently of any particular agent,
message, or application. Users supply the query or target fact, the selected store
and snapshot, and any changes or candidate actions. A violation is one possible
target, not a restriction on Why, What-if, or Min-prevention. The Nova examples below
instantiate these templates; their constants are editable example values.

\subsection{Query}
\textbf{Question.} What facts match this query?
\textbf{Inputs:} a Datalog program, store scope, and snapshot.
The result is a set of variable bindings, or a Boolean for a ground query.
For example, \texttt{?- HasReceivedTag(P, nova\_hiring).} returns principals associated
with that tag in the chosen view. A local query reads one store; Debug queries
operate on the union of independently computed local closures.


\subsection{Why}

\textbf{Question.} Why does this fact hold?
\textbf{Inputs:} a ground \texttt{FACT}, store scope, and snapshot.
A derivation tree identifies the rules and inputs supporting the target, whether it
describes a denial, information propagation, or another derived result.
\textbf{Template:} \(\operatorname{proof}_E(q)\), where \(q\) is a derived fact.
For \texttt{DenyReceive(auditor\_a, mH)}, the proof uses only Auditor A's
local store. Here \texttt{A} abbreviates \texttt{auditor\_a}; indentation denotes
premises. Imported tags are input leaves, not remote derivations fetched from HR or Board.

\begin{lstlisting}
DenyReceive(A, mH)                         [R8]
  Incoming(A, mH)
  MessageTag(mH, nova_hiring)              [R2]
    TransportTag(mH, nova_hiring)
  HasReceivedTag(A, nova_procurement)               [R6]
    Received(A, mP)
    MessageTag(mP, nova_procurement)       [R2]
      TransportTag(mP, nova_procurement)
  HasReceivedTag(A, nova_facility)                  [R6]
    Received(A, mF)
    MessageTag(mF, nova_facility)          [R2]
      TransportTag(mF, nova_facility)
  TagGroup(nova_procurement, nova)
  TagGroup(nova_facility, nova)
  TagGroup(nova_hiring, nova)
  A != board
  nova_procurement != nova_facility
  nova_procurement != nova_hiring
  nova_facility != nova_hiring
\end{lstlisting}

The sender has its own proof for the exported tag: HR derives
\texttt{MessageTag(mH, nova\_hiring)} from a local dependency on \texttt{m0}
and the imported \texttt{TransportTag(m0, nova\_hiring)}. Connecting these proofs
across machines would require additional provenance transport; the current receiver's
proof does not claim that cross-store derivation.

\subsection{What-if}

\textbf{Question.} Would this fact still hold if we changed these inputs?
\textbf{Inputs:} \texttt{REMOVE}, \texttt{ADD}, and a ground \texttt{FACT}.
This evaluates a counterfactual on a copy without changing the live runtime.
\textbf{Template:} specify input facts to
\texttt{REMOVE}, facts to \texttt{ADD}, and a target \texttt{FACT}; evaluate it
in \(\mathrm{Closure}((E\setminus R)\cup A)\).
If A had not received Facility:

\begin{lstlisting}
REMOVE { Received(auditor_a, mF) }
ADD    { }
FACT   DenyReceive(auditor_a, mH)
RESULT false
\end{lstlisting}

Both records of the Facility receive are removed. A would then acquire only a second
part and holds the required HR review capability, so no denial rule applies.

\subsection{Min-prevention}

\textbf{Question.} What is the smallest set of events to prevent so this fact no longer holds?
\textbf{Inputs:} \texttt{EVENTS}, each with its input records, and a ground \texttt{FACT}.
\textbf{Template:} given input state \(E\), target fact \(q\), and a configurable
preventable event set \(\mathcal{P}\), return all minimum-cardinality subsets
\(\Delta\subseteq\mathcal{P}\) whose prevention removes \(q\). The target is not
restricted to a denial. This operation removes event records and recomputes closure;
it does not replay or repair an entire alternative execution history.

Each event \(e\) has input records \(R(e)\); preventing it removes those records and
recomputes derived facts. In this example, only A's two earlier audit receives are
preventable. Configuration, board assignments, and the pending Hiring receive remain
fixed:

\begin{lstlisting}
PREVENTABLE EVENTS P = { eP, eF }
R(eP) = { Received(auditor_a, mP) }
R(eF) = { Received(auditor_a, mF) }
FACT q = DenyReceive(auditor_a, mH)
\end{lstlisting}

The objective is
\[
\underset{\Delta\subseteq\mathcal{P}}{\operatorname{minimize}}\; |\Delta|
\qquad\text{subject to}\qquad
q\notin\mathrm{Closure}\!\left(E\setminus\bigcup_{e\in\Delta}R(e)\right).
\]
Enumerating subsets of \(\mathcal{P}\) gives two minimum solutions:
\(\Delta=\{e_P\}\) or \(\Delta=\{e_F\}\), where \(e_P\) and \(e_F\) denote
\texttt{eP} and \texttt{eF}. Preventing either receive avoids the third-part denial.
This objective removes the specified denial; it does not require the audit to finish.

\subsection{Planning}

\textbf{Question.} Can we reach this goal using the allowed actions?
\textbf{Inputs:} a starting state, \texttt{GOAL}, and \texttt{ACTIONS}.
A locally allowed action may still leave the goal unreachable.
\textbf{Template:} given \(E_0\), goal \(G\), and action set \(\mathcal{A}\), find
\(\pi=(a_1,\ldots,a_k)\) such that every action is allowed and
\(G\in\mathrm{Closure}(E_k)\). A dead end is relative to this action set.
The current Nova planner implements department-to-auditor deliveries; editable inputs
do not make it a general planner for arbitrary tool calls. The independent resource
foundation currently derives FSM reachability only; the protected transition contract
above does not by itself implement general action-path planning.

Here, start earlier: A has received only Procurement, while Facility and Hiring remain
unaudited. The goal is \texttt{Finished(nova)}. The configured actions deliver each
department's tagged rationale to either auditor:

\begin{lstlisting}
GOAL Finished(nova)
ACTIONS {
    Procurement -> A, Procurement -> B,
    Facility    -> A, Facility    -> B,
    Hiring      -> A, Hiring      -> B
}
\end{lstlisting}

The action set is supplied by the application and can be changed. In this task model,
only department-to-auditor deliveries can add the missing \texttt{Covered} facts needed
for \texttt{Finished}, so other sends are excluded. At each state, actions for already
audited parts are also omitted: every remaining allowed action makes progress toward
the goal. Capability grants, policy changes, and other workflows are outside this
configured search, so a dead-end result is relative to these choices.

For each candidate action, the analyzer supplies the message's propagated labels and a
hypothetical \texttt{Incoming} fact. A derived \texttt{DenyReceive} rejects the action;
otherwise, the successor records the allowed receive and recomputes the closure.
The search returns a completion trace, or \texttt{NONE} if none exists:

\begin{rulebox}
\begin{lstlisting}
COMPLETE(E, G, Actions):
    if G in Closure(E): return []
    for a in ProgressActions(E, Actions):
        if Denied(E, a): continue
        E_next = HypotheticalReceive(E, a)
        tail = COMPLETE(E_next, G, Actions)
        if tail is not NONE: return [a] + tail
    return NONE
\end{lstlisting}
\end{rulebox}

This search terminates because each step audits a previously unaudited part, and Nova
has only three parts. Sending Facility to A is allowed immediately, but leaves Hiring
with no legal receiver: A would acquire a third part, and B lacks \texttt{hr\_review}.
That successor is a dead end. Sending Facility to B instead admits the completion
trace \texttt{[Facility -> B, Hiring -> A]}, which derives \texttt{Finished(nova)}
without a denial.


\section{Question Templates by Category}\label{sec:question-catalog}

The categories below describe \emph{what} is being inspected; the analysis modes in
Section~\ref{sec:analysis-questions} describe \emph{how} to answer. For example,
information-flow provenance and communication denials both use Why. The English
questions stay general when the example values are edited.

Braces such as \texttt{\{message\}} denote user-supplied parameters. Unbraced
variables such as \texttt{M}, \texttt{Tag}, and \texttt{Cap} are query outputs.
Bare predicates denote Query patterns (entered with \texttt{?-} in the UI).
\texttt{WHY}, \texttt{WHAT-IF}, and \texttt{MIN-PREVENT} denote analysis operations,
not additional Datalog predicates: they take a target fact, plus \texttt{REMOVE}/
\texttt{ADD} or \texttt{EVENTS} as appropriate. Store scope and snapshot are also
inputs, omitted from the table for readability.

Information and knowledge refer to modeled tags. \texttt{MayDependOn} represents

the selected store's inputs, including imported protocol facts. Resource lifecycle

connected to Nova. Reachability is derived from the FSM for a specified starting state and requires
at least one transition; it does not return an action path.
